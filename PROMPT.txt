## DATA MODELS (Django)
- Vendor: name, slug, description, logo, is_active
- Category: name, slug
- Product: vendor FK, category FK, name, slug, description, base_price,
  is_digital=true, cover_image, is_active
- ProductVariant: product FK, sku, attributes (JSON: platform/region/
  edition/term/denomination), price, stock_count
- DigitalKey: variant FK, code (unique), status (available/assigned/
  revealed/refunded), assigned_order_item FK (nullable)
- Order: customer FK, status (pending/paid/fulfilled/refunded/cancelled),
  total, paymongo_session_id, created_at
- OrderItem: order FK, variant FK, quantity, unit_price, snapshot_name
- Fulfillment: order_item FK, digital_key FK, email_sent_at, brevo_message_id
- RefundRequest: order_item FK, reason, status (requested/approved/
  rejected/refunded), paymongo_refund_id, created_at
- Profile: user FK, role (customer/vendor), vendor FK (nullable)

## EXTERNAL API INTEGRATION — MUST ACTUALLY WORK

### 1. PayMongo (test mode)
- Use Checkout Session API: POST https://api.paymongo.com/v1/checkout_sessions
  with Basic auth (secret key from .env). line_items built from the cart.
- On success, PayMongo redirects to success_url and calls the webhook.
- Webhook handler MUST verify the Paymongo-Signature header before
  trusting the payload. On paid event: set order.status='paid', allocate
  an available DigitalKey per item, set Fulfillment rows, then call Brevo.
- Refund: on approved RefundRequest, call PayMongo Refund API
  (POST /v1/payments/{payment_id}/refunds), mark keys refunded/restocked.
- All keys stay in .env — never hardcode.

### 2. Brevo (transactional email)
- After payment is confirmed and keys are allocated, send one email per
  order via POST https://api.brevo.com/v3/smtp/email with:
  to = customer email, subject = "Your digital keys — Order #<id>",
  htmlContent = order summary + the digital keys.
- Store the returned messageId in Fulfillment.brevo_message_id.
- Also send a vendor notification email when a sale occurs.
- Use a simple HTML template. Read BREVO_API_KEY from .env.

## DIGITAL-GOODS LIFECYCLE (implement this exact flow)
1. Customer selects a variant → backend checks stock_count > 0.
2. Customer clicks Checkout → frontend POSTs /api/checkout/ → backend
   creates Order(status=pending) and a PayMongo Checkout Session, returns
   the checkout_url → frontend redirects.
3. Customer pays with a test card/GCash/Maya → PayMongo webhook fires →
   backend verifies signature → Order.status='paid' → allocate one
   available DigitalKey per item → create Fulfillment rows → call Brevo.
4. Customer lands on success page → sees order summary, gets email with
   the keys → keys can be revealed on the order detail page.
5. Return/Refund: customer files refund request within 24h if the key
   was never revealed → vendor/admin approves in Seller Center →
   backend calls PayMongo Refund API → mark keys refunded → order
   status='refunded'.
